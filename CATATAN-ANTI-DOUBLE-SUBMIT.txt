CATATAN ANTI DOUBLE-SUBMIT - TOMBOL SIMPAN/EDIT/AKSI JANGAN BISA DIKLIK BERKALI-KALI
=====================================================================================
Ringkasan masalah: kalau internet lambat/putus-putus, tombol Simpan/Edit/aksi lain
bisa diklik berkali-kali sebelum request pertama selesai -> request dobel terkirim
ke server (data dobel, state korup, dll). Pola perbaikan pertama kali diterapkan
penuh di quizDigital (2026-09-13). Status tiap halaman ditandai di bagian 4 & 5:
  [✅] = SELESAI/aman      [ ] = belum dicek/diterapkan


1. POLA DASAR
--------------
Sebelum:
  document.getElementById('formX').addEventListener('submit', async (ev) => {
    ev.preventDefault();
    ... validasi ...
    try {
      const r = await apiPost({ ... });
      ...
    } catch (e) { showNotice(e.message, 'error'); }
  });

Sesudah:
  document.getElementById('formX').addEventListener('submit', async (ev) => {
    ev.preventDefault();
    ... validasi (boleh return lebih awal, TOMBOL BELUM di-disable di sini) ...
    const btn = document.getElementById('btnSimpanX');
    btn.disabled = true;
    try {
      const r = await apiPost({ ... });
      ...
    } catch (e) { showNotice(e.message, 'error'); }
    finally { btn.disabled = false; }
  });

Kenapa ini menghilangkan risiko "diklik 3x bersamaan": begitu klik pertama jalan,
`btn.disabled = true` di-set SINKRON, sebelum baris `await` manapun dieksekusi.
Browser tidak pernah mengirim event click/submit ke elemen yang statusnya sudah
disabled -- jadi klik ke-2 & ke-3 diabaikan TOTAL oleh browser sendiri, bukan
cuma "diabaikan oleh kode kita". Hasilnya cuma 1 request yang pernah terkirim,
walau request pertama itu menggantung lama karena internet lambat.


2. LANGKAH-LANGKAH TERAPKAN DI 1 HALAMAN
-------------------------------------------
1) Cari semua pemanggilan yang MENGUBAH data (bukan sekadar baca).
   - Tiap halaman kadang punya nama helper beda-beda (`api()`, `apiPost()`,
     langsung `fetch(API_BASE, {method:'POST', ...})`, dst) -- cek dulu definisi
     helper-nya di bagian atas tag <script> halaman itu sebelum grep.
   - "Mengubah data" = nama action-nya semacam *.save, *.delete, *.trash,
     *.restore, *.toggle, *.publish, *.duplicate, *.setFolder, *.grade,
     *.release*, upload file, dll. Yang cuma BACA (*.get, *.list, *.browse,
     *.results, dst) TIDAK wajib di-disable (boleh saja, tapi bukan prioritas).

2) Untuk tiap pemanggilan itu, cari TOMBOL yang men-trigger-nya:
   - form submit -> tombol `type="submit"` di form itu (kasih `id` dulu kalau
     belum punya, seperti "btnFolderEditSave" yang ditambahkan di quizDigital).
   - tombol biasa -> lihat `addEventListener('click', ...)` yang langsung
     terpasang di tombol itu.
   - delegasi (1 listener di container utk banyak tombol, mis. kartu list) ->
     pakai elemen yang sudah didapat dari `ev.target.closest(...)`, JANGAN
     pakai id statis (tombolnya banyak & dibuat ulang tiap render).

3) Tambahkan `namaBtn.disabled = true;` PERSIS SEBELUM baris `try { await ... }`,
   yaitu SETELAH semua validasi & `return` awal selesai -- supaya validasi yang
   gagal tidak ikut mengunci tombolnya.

4) Nyalakan lagi tombolnya:
   - Default paling aman: `finally { namaBtn.disabled = false; }` -- selalu
     nyala lagi baik request-nya sukses maupun gagal.
   - Boleh dikecualikan (cuma nyalakan lagi di `catch`) HANYA kalau saat sukses
     dialognya pasti ditutup ATAU elemen tombolnya pasti ikut digambar ulang
     dari nol (mis. list yang di-render total lewat `container.innerHTML = ...`
     setelah request sukses).
   - Kalau ragu pilih yang mana: PAKAI `finally`. Salah pilih exception-only
     bisa bikin tombol nyangkut disabled selamanya setelah sukses.

5) Tes manual di browser: DevTools > Network > throttle "Slow 3G", buka
   halamannya, klik tombol Simpan/aksi itu 3-5x cepat berturut-turut, pastikan
   cuma 1 request yang muncul di tab Network dan tombolnya nyala lagi setelah
   request selesai (baik sukses maupun sengaja bikin gagal, mis. matikan wifi
   sebentar).


3. KASUS KHUSUS / JEBAKAN (ditemukan pas kerjain quizDigital)
----------------------------------------------------------------
a) Tombol di dalam dialog konfirmasi generik (openConfirm/confirmOkBtn) --
   SUDAH AMAN TANPA perlu ditambah apa-apa, KARENA dialognya di-close() duluan
   secara sinkron sebelum request async-nya jalan. Begitu dialog close,
   tombolnya hilang dari layar -- tidak mungkin diklik lagi secara fisik.
   Contoh: konfirmasi hapus/duplikat quiz & folder di quizDigital.
b) Tombol di dalam picker yang menutup dialog-nya dulu baru memanggil callback
   (mis. folder browser "Pilih folder ini") -- sama, sudah aman by design
   dengan alasan yang sama seperti poin (a).
c) Grup tombol yang saling terkait (mis. 3 tombol Benar/Salah/Auto untuk 1
   soal di quizDigital) -- disable SEMUA tombol dalam grupnya sekaligus, bukan
   cuma tombol yang diklik. Kalau cuma yang diklik yang di-disable, tombol
   sebelahnya masih bisa diklik dan bikin 2 request yang saling balapan.
d) Tombol yang TIDAK ikut digambar ulang setelah sukses (tombol statis di
   luar list yang di-render ulang, mis. "Rilis Hasil" di quizDigital) -- WAJIB
   pakai `finally`. Kalau cuma re-enable di `catch`, begitu request-nya sukses
   tombolnya nyangkut disabled selamanya (elemen DOM-nya sama persis, tidak
   pernah diganti baru).
e) Input file (upload gambar/audio/dokumen) -- disable elemen
   `<input type="file">`-nya sendiri selama proses upload, dan reset
   `.value = ''` di `finally` juga (supaya user bisa pilih file yang sama lagi
   kalau upload gagal).
f) JANGAN disable tombol SEBELUM validasi selesai. Kalau validasi gagal dan
   kode `return` lebih dulu, pastikan baris `disabled = true` belum kelewat
   dieksekusi -- kalau kepencet, tombolnya nyangkut nonaktif padahal tidak ada
   request yang pernah jalan.
